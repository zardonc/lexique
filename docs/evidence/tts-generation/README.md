# TTS 模型生成优化实验

2026-11-01，用户要求先脱离具体业务场景优化模型生成并验证推荐方案。只使用现有准入的 Supertonic 3 int8、sherpa-onnx 2.0.1 / ONNX Runtime 1.28.2 和现有 48 kbit/s Opus 编码；不修改产品调用、缓存、卡片或学习数据，不增加依赖或更换模型。

## 推荐结论

本机持续生成的推荐是：**常驻一个模型，模型推理线程设为 2，最多 12 个共享模型的生成调用同时执行，关闭线程空转，保持法语 / 正常速度 / 8 步。** 这是已覆盖 CPU 配置中的吞吐、内存折中，不是所有设备和文本上的全局最优，也没有接入应用。

固定种子的 24 词、三轮中位数从复用模型串行的 23.50 秒降到 5.63 秒，持续吞吐约为 4.17 倍，批量时间减少约 76%。**包含启动、资源验证、加载、预热和退出的完整进程**则为 25.77 → 10.01 秒，约 2.57 倍；不能把热模型收益直接解释为第一次生成的收益。

单条延迟优先时，推荐已加载模型、4 推理线程、串行调用；12 词对照的单次推理中位数约 0.98 秒，12 路满载时约 2.69 秒。并发改善一批文本的完成时间，单个请求会争用 CPU；4.26 条 / 秒的吞吐倒数不是单条生成延迟。直接调用与单后台线程没有明显性能差别。

4 / 2 步虽然更快，但有满幅越界的数值证据且音质未获人工确认，因此不纳入保持现有音质的推荐。当前运行库请求 CUDA 会明确回退 CPU，没有 GPU 加速测量。

## 实验计划

1. 保留当前逐词启动的真实 worker 作为对照。复用 worker 现有资源哈希、输入、采样和编码校验，在隔离进程内加载模型一次，测准备时间及模型已加载后的连续生成。
2. 先固定法语、正常合成速度、8 步，比较 1 / 2 / 4 / 8 / 16 推理线程。按 ONNX Runtime 官方线程建议比较默认空转、关闭空转和短时退避空转；选项通过现有 sherpa-onnx provider config 转发，不更改库。
3. 先比较一个模型的 2 / 4 线程并发与 2 / 4 独立模型进程，再在本机内存允许时探测 8 个独立进程和 8 / 12 / 16 个共享模型并发任务。每次生成使用独立的 GenerationConfig 与固定种子，检查请求身份及有限、非静音、44.1 kHz 单声道输出；保留原始 PCM 和编码音频，比较串行 / 并发结果，不能仅凭 Python 释放 GIL 宣称所有共享模型都线程安全。另用应用当前的随机种子路径补验，并保留工作线程池跨预热和计时阶段的生命周期，避免重新初始化线程局部 RNG。
4. 用 12 个不同长度及拼写的法语单词筛选；候选再独立重复并交叉验证六个短句、两种声线及较长连续负载。额外对照直接串行调用与单工作线程调用，排除测试调用方式本身的影响。按单条延迟、持续吞吐、CPU 时间和同时采样的工作集 / 私有提交量分别判断，不能把最多并发当作最优。
5. 单独试验 4 / 2 步，保留与 8 步同文本、声线和种子的实际编码试听样本。格式 / 数值验证不证明发音正确，未经人工试听不把减少步数纳入音质保持的推荐。

所有测量串行运行，一次配置可在内部并发。每次配置的执行硬限 60 秒，超时终止该次进程树；产物仅写入 `target/issue-24/` 的新子目录。首次读取不当作冷盘，不驱逐系统缓存、不修改电源或安全设置。其他设备 / 平台和 GPU 运行库不在现成 CPU 实测结论中。

参考：[ONNX Runtime 线程管理](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)；[sherpa-onnx 固定提交的会话选项](https://github.com/k2-fsa/sherpa-onnx/blob/af2d8d81dbfa61c4cea4c568da78f3982edca005/sherpa-onnx/csrc/session.cc)和[Supertonic 随机种子边界](https://github.com/k2-fsa/sherpa-onnx/blob/af2d8d81dbfa61c4cea4c568da78f3982edca005/sherpa-onnx/csrc/offline-tts-supertonic-impl.cc)。上游 Apache-2.0；本实验复用项目已存在的 worker，不复制上游实现。

## 复现入口

```powershell
$ttsPython = (uv python find).Trim()
& $ttsPython -B -X utf8 scripts/measure_tts_generation.py --self-check
& $ttsPython -B -X utf8 scripts/measure_tts_generation.py .tooling/issue-15-opus/speech-stage target/issue-24/tts-new-run --configs 'serial,1,4,8,on' 'shared,12,1,8,on' 'shared,12,2,8,off' 'shared,16,2,8,off' 'process,8,2,8,off' --repeats 3 --cycles 2
& $ttsPython -B -X utf8 scripts/measure_tts_generation.py --runtime-checks .tooling/issue-15-opus/speech-stage target/issue-24/tts-new-runtime-check
& $ttsPython -B -X utf8 scripts/verify_tts_generation.py --self-check
& $ttsPython -B -X utf8 scripts/verify_tts_generation.py
```

输出目录须是不存在的新目录。`mode,workers,threads,steps,spin` 分别为执行方式、并发调用 / 进程数、模型推理线程、合成步数、空转策略；`off` 通过本地 `cpu.config` 转发 `SessionConfig.session.intra_op.allow_spinning=0` / `SessionConfig.session.inter_op.allow_spinning=0`。关闭空转本身没有在串行对照中提速，推荐是经过测量的参数组合。

独立核验脚本读取本次固定命名的 11 个目录及 `tts-runtime-check-v2-20261101`，不是任意一次新跑结果的通用汇总器。所有目录齐备后，可用 `--summary <明确的 JSON 路径>` 导出汇总，或 `--listen <target/issue-24 下的新目录>` 再导出试听；完整矩阵、每个配置的三轮时间、过程 / 推理 / 服务时间、CPU、内存和对应脚本 / worker 哈希见 [results.json](results.json)。

原始性能 runner 在筛选阶段迭代过，各轮哈希单独记录。当前随机种子及步数矩阵使用的完整 runner 字节归档于 `target/issue-24/tts-measured-source-20261101/measure_tts_generation.py`，SHA-256 为 `4f60e3e0e58d995ddea50b5b03719e6402a99924456bcb42918f3cd904556bdd`，与两轮记录一致。当前入口在该计时代码之外追加 GPU / 输入检查；不能用当前整文件哈希冒充历史轮次哈希。归档的移动位置用于审计，复现应使用仓库 `scripts/` 入口与现有资源。

## 已完成的固定种子对照

Windows 11 Home 10.0.26300、Ryzen 9 8945HS（8 核 / 16 逻辑处理器）、32 GB RAM，保持原有“平衡”电源方案。现有打包运行库为 sherpa-onnx 2.0.1，自报源码 `af2d8d81`，ONNX Runtime 1.28.2；有 NVIDIA RTX 4060 Laptop / AMD 780M 硬件，但以下均为 CPU 推理，不把硬件存在当成 GPU 已使用。

12 词、三轮对照（毫秒中位数，法语女声 / 8 步；包括编码和证据文件保存，不含应用 IPC / 缓存发布 / 播放）：

| 执行方式 | 一批 12 词 |
| --- | ---: |
| 当前真实 worker，每词重新启动 | 25,504.4 |
| 一次加载模型，2 推理线程，串行 | 12,704.7 |
| 一次加载模型，4 推理线程，串行 | 11,303.4 |
| 一次加载模型，4 推理线程，短空转退避 | 11,384.1 |

直接在主线程串行调用和单工作线程串行调用另行对照，结果接近，没有把线程池封装开销误当成优化收益。固定种子对照为 `42 + request_id`；真实逐词 worker 保留当前随机种子默认值 `-1`，作为完整进程时间对照，不将其音频与固定种子 PCM 做相等断言。

24 词、三轮模型已加载后的持续生成（毫秒中位数；同一 12 词各出现两次，固定种子 / 女声 / 8 步）：

| 模型与并发 | 模型推理线程 / 等待策略 | 24 词总时间 | 采样私有内存峰值 MiB | 活跃 CPU 时间中位数，秒 |
| --- | --- | ---: | ---: | ---: |
| 一个模型，串行 | 4 / 默认空转 | 23,502.7 | 773.9 | 108.2 |
| 一个模型，8 路共享 | 1 / 默认 | 6,601.2 | 1,078.7 | 50.5 |
| 一个模型，12 路共享 | 1 / 默认 | 5,761.3 | 1,216.0 | 60.0 |
| 一个模型，16 路共享 | 1 / 默认 | 5,963.6 | 1,477.8 | 62.0 |
| 一个模型，12 路共享 | 2 / 关闭空转 | 5,634.7 | 1,215.9 | 63.7 |
| 一个模型，16 路共享 | 2 / 关闭空转 | 5,788.0 | 1,482.8 | 64.3 |
| 八个独立模型进程 | 各 2 / 关闭空转 | 5,658.8 | 6,171.3 | 62.2 |

12 路 / 2 线程 / 关闭空转的三轮为 5,634.7、5,657.6、5,612.7 毫秒；16 路为 5,788.0、5,834.7、5,564.8 毫秒。16 路有一次更快，但未获得稳定优势，采样内存更高。独立进程吞吐接近，却加载八份模型。固定种子矩阵全部 504 份 PCM 与串行参考逐字节相同。

12 路 / 1 线程也接近最快组，时间只差约 2%，CPU 时间略低；没有统计证据宣称 2 线程必然优于 1 线程。选择 2 线程 / 关闭空转是本次跨负载确认后的建议，而不是单轮参数排名。

表中的私有内存是进程私有提交量，另保存工作集；50 毫秒采样后取同时占用的最大值，包含模型准备和预热，不是分配器的绝对峰值。推荐组私有提交峰值 1,215.9 MiB、工作集峰值 634.6 MiB；串行分别为 773.9 / 290.9 MiB，不能把提交量直接当作驻留 RAM。CPU 时间是所有本次进程在计时阶段的用户态 + 内核态累计时间，不能解释为耗电量。机器上其他进程未停止，后续确认轮记录背景负载，早期 pilot 未记录的字段为 null；不是无干扰实验室或冷盘测试。时间分组 / 原始逐次结果均保留，不只报告最快一轮。

## 跨文本、声线和较长负载确认

均为三轮中位数，8 步、模型已加载后的批量时间：

| 负载 | 串行 / 4 线程 | 共享 12 路 / 2 线程 / 关闭空转 | 共享 16 路 / 2 线程 / 关闭空转 |
| --- | ---: | ---: | ---: |
| 6 个短句各生成两次，男女声交替 | 21,710.2 ms | 5,746.1 ms | 5,751.4 ms |
| 48 个词输入，男女声交替 | 47,435.1 ms | 11,224.7 ms | 11,088.6 ms |
| 24 个词，应用当前随机种子路径 | 23,383.1 ms | 5,661.1 ms | 5,900.4 ms |

句子串行增至 8 推理线程为 21,091.0 ms，仅略快且消耗更多 CPU。48 词长负载中 16 路中位数略优于 12 路，因此不声称 12 路总是最快；其跨负载优势不稳定，内存成本更高。每个短句没有穷尽男女两种声线的完整组合，48 词使用同一 12 词循环四次，这不是 48 个不同词或无限时长压力测试。

当前随机种子使用 worker 原有的 `GenerationConfig.extra={"lang":"fr"}`，没有显式 seed，保持工作线程池跨预热 / 计时阶段存活。该轮并发加速仍约 4.13 倍，但音频天生随机，不对其与固定种子或其他请求的 PCM 作相等断言。

## 合成步数与试听

18 个不同输入（12 词 + 6 句、男女声交替），同文本 / 声线 / 固定种子、12 路 / 2 线程 / 关闭空转，三轮：

| 步数 | 批量时间中位数 | PCM 最大绝对峰值 | 18 个输入中峰值超过 1 的数量 |
| --- | ---: | ---: | ---: |
| 8 | 7,071.3 ms | 0.590 | 0 |
| 4 | 3,822.4 ms | 1.165 | 1 |
| 2 | 2,209.4 ms | 2.193 | 11 |

同输入的三个步数采样数相同，固定种子三轮 PCM 也重复一致。4 步 / 2 步分别约快 1.85 / 3.20 倍，但峰值超过浮点音频的常见满幅范围，有削波或失真风险；格式有效和同样时长不能证明发音准确或自然。

[试听页](../../../target/issue-24/tts-listen-opus-20261101/listen.html)含 `école` 女声、`bonjour` 男声及两句男女声的 8 / 4 / 2 步，共 12 个实际 48 kbit/s Ogg Opus。源 PCM / 音频哈希记录在同目录 `manifest.json`。初次 16-bit WAV 导出因 2 步超满幅而拒绝，部分初探文件保留；最终使用原实际编码音频，不通过逐文件归一化掩盖幅度差异。机器合成披露和人工质量待确认已在页面注明。

## GPU 与失败处理

通过现有运行库初始化 `provider="cuda"`，模型加载成功，但原生日志明确记录 `Available providers: CPUExecutionProvider, . Fallback to cpu!`。GPU 初始化成功与回退 CPU 必须分开判断；本机虽有 RTX 4060 Laptop / AMD 780M，当前包没有可用 GPU 执行器。本轮没有安装 CUDA / DirectML 运行库、替换模型或测 GPU 生成，不能给出 GPU 加速承诺。

7 项真实验证边界检查全部通过：空文本、超过 200 字符、控制字符、非字符串文本、非法声线、路径形式请求编号、第一份模型资源的错误哈希。检查执行现有 worker 提取的校验，拒绝请求没有写出音频；坏资源仅为新隔离目录的小 fixture，没有修改原资源。

## 本轮验证与限制

- `measure_tts_generation.py --self-check` 与 `verify_tts_generation.py --self-check`：通过；包含 probe 编译、无效配置、输出边界、响应身份、非有限度量、损坏 PCM 和非法 Opus 元数据的拒绝。
- `measure_tts_generation.py --runtime-checks ...`：7 项失败路径通过，CUDA 回退 CPU 的原始诊断、运行库自报版本和来源脚本保留。
- 11 个性能目录合计 122 次配置轮次，全部完成且每次执行硬限 60 秒；2,214 个实际 Ogg Opus 大小 / 单声道输入采样率元数据核验通过。
- 2,178 个 PCM 的实际 SHA-256、采样数、有限 / 非静音、时长、峰值、RMS 回读通过。其中 1,890 个固定种子输出重复一致；1,764 个与可用串行参考逐字节一致（包括该参考本身）。混合步数矩阵的 6 个句子种子没有串行参考，其 18 份 8 步输出只证明重复一致。288 个当前随机种子输出仅验身份与音频，不作相等断言；36 个真实逐词 baseline 没有原始 PCM。
- 每轮 summary 与原始 trial 核对、配置 / 请求 / 重复计数、批量与完整进程中位数、同时采样内存峰值核验通过；所有结果保留原始时间，不能把吞吐倒数或服务时间误作排队后的端到端延迟。
- 当前两个 Python 入口及已保存 probe 的语法、12 个试听文件实际哈希核验通过。Obscura 检查页面结构，但其环境不提供真实音频解码；按本地环境规则改用 Chromium，对完整 Ogg Blob URL 核验 12 个控件全部加载正时长、无错误、保持暂停 / 正常速度 / 无自动播放。临时 HTTP 服务不支持 Range，直接流式 Ogg 的部分 duration 为 Infinity，没有当作文件损坏或有效时长通过；完整文件 Blob 的元数据结果保存在试听目录 `browser-check.json`。未调用实际播放或增加人工音质结论。
- 本地文档链接及 Git 空白检查通过；临时 HTTP 服务和本轮两种浏览器的检查页均关闭。本轮只增加独立 Python 实验与文档，不把此前 TS / Rust / 原生 UI 套件记为本次重新通过。

只验证这一台 Windows x64 机器、现有运行库和有限的法语输入；没有温度 / 电池功耗、长时间空闲内存、低端机器、其他平台或 GPU 数据。12 路会占用更多内存并增加单个请求的 CPU 争用；共享模型在本次固定种子、跨线程 / 进程对照中结果一致，不等于所有上游模型或版本都有线程安全保证。减少步数的音质仍待人工确认。产品没有接入常驻模型、任务调度、取消、故障恢复或缓存发布，本次不认定这些业务能力或发行验收已完成。
