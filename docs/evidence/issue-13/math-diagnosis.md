# 跨平台数学差异诊断与修复

日期：2026-10-26。结论：未修改的 FSRS 6.6.2 在本机 Windows x64 与 WASM 中使用的平台数学结果不同；差异可脱离 FSRS 和全部应用依赖独立复现。没有发现锁定依赖损坏、工具链错配或 Debug / Release 配置导致原失败的证据。修复在固定依赖的标量调度数学路径实施，应用步骤、时间规则及整数比较不变。

## 假设与验证

在测试前依次列出三个可证伪假设：依赖 / 工具链 / 旧产物不一致；优化配置导致差异；上游平台数学实现不同。

| 探针 | 结果 | 含义 |
| --- | --- | --- |
| 原 `node scripts/check-scheduling.mjs` | 退出 1，两个固定反例相差一天 | 原失败稳定重现 |
| 检查锁定版本、编译器与覆盖配置 | Rust/Cargo 1.99.1，LLVM 23.1.1；无全局 Cargo config 或 RUSTFLAGS / profile 覆盖 | 未发现工具链 / 配置错配 |
| 官方发布包 SHA-256 和 model.rs 与固定 tag 对照 | 包哈希符合原锁文件；model.rs 与 v6.6.2 对应 | 未发现依赖损坏或串版本 |
| 独立 crate 只直接调用 FSRS，隔离 target 重建 | 两个反例仍然不同 | 排除 JSON、时区、步骤、应用缓冲区及旧构建缓存 |
| 同一独立 probe 的 Debug / Release | 两者均得到原生 10,742 / 1,425 天、WASM 10,741 / 1,424 天 | 切换优化配置不能修复 |
| 已安装 Rust 1.91.1 / LLVM 21.1.2 原生重建 | 同样为 10,742 / 1,425 天 | 不支持“本次新编译器才引入偏差”的假设；未安装或切换项目工具链 |
| 零第三方依赖的 `exp` / `powf` probe | 双端输入相同，各相差 1 ULP | 直接定位平台数学差异 |
| 只将调度路径的数学调用改为固定 libm | 全部 71+4,096 向量通过，记忆差为零 | 最小原因修复有效，无须改变应用调度规则 |

两个首次不同的操作：

| 操作和 f32 输入 | Windows 原生值 / bits | WASM 值 / bits |
| --- | --- | --- |
| `exp(0.014672648161649704)` | 1.014780879020691 / 1065477207 | 1.0147807598114014 / 1065477206 |
| `powf(837.2720947265625, -0.16660000383853912)` | 0.32587453722953796 / 1051121927 | 0.3258745074272156 / 1051121926 |

第一个反例在增长因子的 `exp` 首次不同；第二个反例在稳定度的 `powf` 首次不同。传播后原始间隔分别为 10741.506 / 10741.49609375 和 1424.5 / 1424.499755859375，跨过半天取整点。[Rust 官方文档](https://doc.rust-lang.org/std/primitive.f32.html#method.exp)说明此类浮点函数的精度可随平台和 Rust 版本变化。这是跨端严格整数排程契约与依赖默认数学实现的兼容问题；没有据此判定某个端的值为唯一正确答案。

## 独立复现

```sh
node scripts/diagnose-scheduling-math.mjs
```

脚本只用项目固定工具链编译 [math-probe.rs](math-probe.rs)，不依赖 Cargo、FSRS、JSON、时区、应用代码或网络。输入经 `black_box` 避免常量折叠，再实际执行 native 和无宿主导入的 WASM；逐项比较返回的 f32 位模式。结果写入 `target/issue-13-math/result.json`，不一致时退出 1。该诊断命令在本机修复后仍应失败，因为它直接检测标准库的平台数学，不使用修复后的依赖；不是正式准入命令或 CI 必须通过的检查。其他平台可能得到相同结果，不预设必须失败。实测见 [机器记录](math-windows-x64.json)。

原失败报告保留为 [未打补丁的对照](conformance-unpatched-windows-x64.json)。诊断期间一次全 workspace 的 WASM 依赖树查询曾因受限工具环境无法解析 crates.io 而失败；本节的独立编译均能使用本地缓存完成，该网络限制不能解释已经运行的两个产物的数值差异。项目全局环境未改动。

## 修复范围与复验

固定官方 6.6.2 源码与默认参数，使用显式 [本地补丁](../../../vendor/fsrs-6.6.2/LEXIQUE-PATCH.md)。新增 `libm = "=0.2.16"` 且关闭默认 features，使 `FSRS::default().next_states` 标量调度路径的 `ln` / `exp` / `powf` 共用通用 Rust 实现；表达式及其运算顺序保持不变。[libm 官方项目](https://github.com/rust-lang/compiler-builtins/tree/main/libm)作为实现来源，[单独许可](../../../resources/libm-0.2.16/LICENSE.txt)完整保留。没有全局替换 C 数学符号，没有改取整方式或放宽比较。

[源码审计](vendor-audit.json)逐一比较官方归档的 40 个文件，仅 `Cargo.toml` 和 `src/model.rs` 不同；完整差异保存在 [补丁](portable-math.patch)。原包 checksum 因使用本地 patch 不再出现在 Cargo.lock 的 fsrs 条目中，归档 checksum、原提交和每个文件的修改前后 SHA-256 由该审计保存；libm 的精确版本及归档 checksum 仍由锁文件验证。

调度输出显式记录 `fsrs-rs/6.6.2+libm-0.2.16`。这是本地兼容修订，不冒称未修改的上游包；旧标识即使参数相同也拒绝重放，避免静默改变旧历史。新增公开入口回归验证该拒绝行为，原两条跨端反例继续要求严格相等。未打开或迁移用户库。

最终 Windows x64 release 原生 / 实际 WASM：71 个固定向量、4,096 个校准向量全部通过，stability / difficulty 最大实测差为零；阶段、整数天、步骤秒数、到期时刻和元数据严格相等。完整新结果见 [修复后对照](conformance-windows-x64.json)。同样重建并执行 [Debug 对照](conformance-debug-windows-x64.json)，71+4,096 样例也通过且记忆差为零，排除修复只在 release 生效。这证明已运行的样例与平台，不是对任意输入或未运行架构的数学证明。其他验证命令与边界见 [总记录](README.md)。
