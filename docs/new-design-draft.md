一. 缓存保留策略

**结论：保留有归属的单词音频，不按 7 天清理。** 保持"归属豁免 TTL"这条规则，并把它显式化：

| 项目 | 建议 |
| --- | --- |
| 归属豁免 | 把"有归属则不过期"写成 GC 谓词（NOT EXISTS 归属），并加回归测试：任何 GC 路径都不删有归属的音频 |
| 归属转移 | 查询音频被加入生词本时，在同一事务里清除其过期时间。若已过期被清空，则按普通缺失处理，进入生成队列 |
| 多版本 | 在 words 或音频表上维护 current_audio_id（或"每词每声线一个当前版本"的部分唯一索引），不要每次用"最近生成的可用版本"排序查询。切换声线后，旧版本在新版本稳定一段时间后（如 7 天）再 GC |
| 总容量预算 | 只对无归属音频（临时查询、被取代版本、孤儿）设软上限，如数百 MB，按 LRU 清理。有归属音频不计入淘汰，但在设置页展示占用 |
| 非确定输出 | 这一点支持保留：学习者长期听到的是同一份音频，重新生成会改变听觉线索 |
| 查询音频是否续期 | 当前"播放和查询不续期"可以接受。如果想让用户最近用过的查询词保留更久，改为滑动期限即可，这是产品选择 |

二. 生成优先级（解决批量积压）：缺失音频的卡被排除出队列，因此生成顺序直接决定可复习性。建议后台队列按层级调度

a. 交互请求（保留 1 个槽位，已有）。
b. 持久队列中靠前的卡，约取额度的 2 倍（≈150 张）。
c. 明天到期的卡。
d. 其余已到期的卡。
e. 未到期的卡。

每层内按 `position` 或到期时间排序，并按语义键去重。批量导入后用户当天需要的只有几十张卡，约一两分钟即可就绪，其余在后台慢慢补齐。

三. 队列查询相关

```text
音频发布(一次) ──► audio_assets 表记录 状态/大小/hash/文件指纹
                         │
队列刷新 ──► DB 候选流(按 position/分类) JOIN audio 状态  ← 无文件访问
                         │ 逐张取，凑满额度即停
                         ▼
        队首 M 张(如 5～10) 做严格句柄校验 ─► 失败：标记 suspect、入生成队列、继续取下一张
                         │
播放(第 8 步) ──► 读取一次字节 → 校验 → 用同一份字节解码播放（最终放行点）
```

措施：

1. **校验前移到发布时。**
    - 发布流程为：写临时文件 → 校验头/大小/SHA-256 → 原子重命名 → DB 事务记录 `audio_assets`（含 size、mtime、Windows 文件 ID）和 `current_audio_id` → 发出 `audio_ready` 事件。
    - 队列查询不再读文件，只读状态。
2. **启动时对账，代替每次查询的全量读取。**
    - 用目录枚举（Windows 的 `FindNextFile` 在枚举时就带出大小、修改时间和属性）一次性对比 DB 记录，不需要逐个打开文件。（风险点：MacOS需做相应适配）
    - 发现大小或时间不符、重解析点或缺失，则标记 suspect 并后台低优先级重新校验。
    - 这一步覆盖"截断/意外替换/符号链接"。
3. **额度限定的惰性选取。**
    - 候选流在 DB 里按优先级排好，遇到听音卡检查 `audio_state=ready`，凑满剩余额度就停。
    - 额度是在评分时消耗的，所以跳过坏卡取下一张不会破坏语义。
    - 最坏情况（全缺音频）也只是扫 DB 状态列，不涉及文件。
4. **队列摘要用聚合查询。**
    - `audio_pending` 返回计数加前 N 个词 ID（如 100），不要把 1 万个 ID 序列化给前端。
    - 唤醒时间用 `MIN(due)` 的索引查询。
5. **评分后增量更新，不再全量重扫。**
    - 队列服务保持一个"已验证的预读缓冲"（如前 50 张）。
    - 评分后只做：移除当前卡 → 若进入学习/重学则按规则插回 → 检查刚到期的分钟学习卡 → 缓冲低于阈值时后台补充。
    - 日切换（凌晨 4 点）、设置变更、时钟异常、跳过列表变更触发**全量重算**（现在 DB-only，应是几十毫秒）。
6. **统一"额度为 0"的语义。**
    - 你提到的"两项上限都为 0 时桌面跳过音频检查，连日内听音卡一起过滤"，在新设计里不需要这个快捷路径。
    - 日内学习卡不占额度，应走独立路径并始终可见。
    - 建议加回归测试，并把此项列为需要修复的一致性问题。

**预期效果（目标，需实测）**：进入复习页的耗时变为"DB 候选流 + 10 次左右的严格校验"，不再随 N 线性增长，目标 <100 ms；评分后切卡目标 <20 ms。


四. 其余细节

2. 音频过期时间

| 级别  | 类型           | 保留                           |
| --- | ------------ | ---------------------------- |
| T0  | 有归属的当前音频     | 不过期                          |
| T1  | 被取代的旧版本      | 新版本就绪后 14 天                  |
| T2  | 孤儿音频（词或卡被删除） | 7 天宽限期（沿用现有）                 |
| T3  | 临时查询音频       | 7 天（沿用现有；若想让常查词保留更久，可改为滑动期限） |

2. 逐卡/逐词查询

当前流程，1 万个单词至少产生约 3 万次 SQL（进度、音频键、音频资产各一次），再加 1 万次文件检查。16 个线程能掩盖一部分等待，但无法消除调用次数。之前"音频检查约占 98.4%"的历史分解，应当理解为"SQL N+1 加文件 I/O"的合计。只做校验前移而不合并 SQL，会留下一大块成本。

另外，因为已经没有旧格式音频，**"旧缓存哈希登记"这条路径可以整段删除**，包括读路径里的写入和它的分批事务。

合并成一条 JOIN（示意，表名和列名按实际结构调整）

```sql
SELECT c.id, c.kind, c.word_id, p.state, p.due, p.step,
       a.state AS audio_state, a.size, a.mtime_ns
FROM cards c
JOIN card_progress p      ON p.card_id = c.id
LEFT JOIN words w         ON w.id = c.word_id
LEFT JOIN audio_assets a  ON a.id = w.current_audio_id
WHERE c.paused = 0
  AND p.due <= :now                      -- 到期过滤下推，不再逐张排除
  AND (c.kind <> 'listening' OR a.state = 'ready');
```

配套的修改：

- **`words.current_audio_id`（当前版本指针）**：在发布和 GC 的同一事务里维护。发布时指向新版本；GC 清理某版本时，若它是当前版本，则改指向其他最近生成的可用版本，没有则置空。这样"最近生成的可用版本"不再需要每次排序查询。
- **`audio_assets` 状态列**：`ready / pending / suspect / gc_pending`，同时存 `size`、`mtime_ns`、文件 ID、SHA-256、`expires_at`（有归属则为空）。
- **`audio_pending` 摘要**：单独一条聚合查询统计 `listening` 且到期、音频非 `ready` 的数量，ID 只取前 100 个。
- **会话级跳过列表**：数量小，放在 Rust 里过滤即可。
- **索引**：`card_progress(due)`、`cards(paused, kind)`、`words(current_audio_id)`、`audio_assets(state)`。用 `EXPLAIN QUERY PLAN` 加测试。

3. 音频旧版本保留14天

> "旧版本"指同一词被新版本取代后的旧文件，比如切换声线后重新生成，或损坏后重新生成。或更换生成模型

**推荐：从新版本成为"当前版本"起保留 14 天。** 同时满足这些条件：

1. 新版本状态为 `ready` 并已通过校验，才开始计时。新版本失败时，旧版本继续当当前版本，不进入 GC。
2. 每个"词 + 声线"最多保留 1 个被取代的版本，更早的直接清理。
3. 被取代版本合计超过一个软上限（如 200 MB 或缓存占用的 20%）时，按最旧优先清理。
4. 始终保证：有归属的词至少有一个 `ready` 版本，除非该词本来就没有音频。

理由：

- 单文件约 9 KB，保留成本很低，所以这个期限主要是为了安全：能回滚、能处理新版本被发现有问题的情况，不是为了省空间。
- 14 天足够覆盖用户试用新声线、发现不满意、改回的窗口。
- 将来做多端同步时，其他设备可能还在引用旧版本，那时建议改成 30 天，或改为"所有设备确认切换后才可清理"。把期限做成常量或设置项，现在先定 14 天。

4. 执行顺序

**P0**：建立基准：1k/10k/50k 词；全新卡/混合；音频 0%/50%/100% 缺失；冷/热文件缓存；建 `audio_assets` 状态、`current_audio_id`、索引；把 N+1 合并为一条 JOIN；删除旧格式哈希登记；查询路径不再打开文件。
**P0**：GC 谓词写成"有归属不过期"并加回归测试；归属转移事务化；新增被取代版本的 14 天规则。
**P1**：额度限定的惰性选取；T1 队首校验；播放失败自动重生成；队列服务 actor 和单写线程；读连接池缩到 2～4；修复"额度为 0"的语义。
**P1**：生成优先级调度，并比较合成并发 1/2/3 的实际吞吐。
**P2**：评分后增量更新与预读缓冲；启动对账；定期完整哈希巡检；下一张音频预解码。

5. 验证方案

- **差分测试**：惰性/增量结果与"全量严格校验"结果对比，覆盖随机数据。
- **故障注入**：截断、替换、符号链接/重解析点、头损坏、哈希不符、文件缺失、权限错误。
- **崩溃恢复**：重命名与 DB 提交之间、GC 的 `gc_pending` 与删除之间中断。
- **并发场景**：评分时重算、`audio_ready` 风暴、撤销、日切换。
- **额度边界**：额度 0、日内学习卡、两张同词卡分别计数。

5. 数据库优化

a. **消除 N+1。** 现在"读取进度、逐卡找音频"若是逐卡查询，改为单条 `JOIN`：`cards LEFT JOIN audio_assets ON current_audio_id`。不需要 16 个连接各自查询。
b. **索引（如尚未具备）**：未暂停卡的 `(paused, state, due)` 部分索引；`review_queue_entries(position)` 唯一索引；音频状态列索引；GC 用的 `gc_pending`/过期时间索引。用 `EXPLAIN QUERY PLAN` 做测试，防止回归。
c. **不要把整张卡表载入应用层再筛选。** 分类和筛选尽量下推到 SQL，只取队首需要的列。
d. **一致读快照。** 队列刷新在一个读事务里读取设置、额度、候选，避免和评分事务交错导致不一致。
e. **评分事务。** 进度、评分记录、额度、撤销快照、队列条目变更放进一个 `BEGIN IMMEDIATE` 事务；复用 `prepare_cached`。
f. **PRAGMA。** `journal_mode=WAL`、合适的 `busy_timeout`、`temp_store=MEMORY`，可选 `mmap_size`。`synchronous=NORMAL` 在 WAL 下不会损坏数据，但断电时可能丢最后一次提交，需要你权衡"最后一次评分丢失"的可接受性。批量写入后跑 `PRAGMA optimize`。
g. **位置重编号。** 间隙不足时，用一条带窗口函数的 `UPDATE`（`ROW_NUMBER() * 1000000`）在事务里批量重排，不要逐行更新。
h. **GC 批量。** 每批 100 项保持在一个事务里，先 `gc_pending` 后删文件，这部分流程已合理。

6. 多线程优化

| 组件             | 建议                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| 写入             | 单写线程（actor）持有唯一写连接，评分、队列变更、音频登记通过 channel 串行提交，避免 SQLITE_BUSY 和写写竞争                                                |
| 读取             | 小读连接池（2～4 个），WAL 模式；阻塞的 SQLite/文件 I/O 放在 spawn_blocking 或专用线程池，不占 async worker                                     |
| 队列服务           | actor + 修订号：事件（评分、暂停、audio_ready、定时器、日切换）进入后合并为"脏标记"，当前计算结束后尾随重算一次；结果带修订号，通过 watch 通道发布；过期结果丢弃；计算循环里检查取消令牌         |
| 校验线程池          | 现在 16 个并行检查对应 16 个连接，改为 DB 状态后不再需要。严格校验只对队首少量卡，用 2～4 个线程即可。对账扫描用低优先级线程并分块（如每块 200 个）让出 CPU。暂不考虑16线程，以2/4/8作为基准进行测试 |
| 合成调度           | 优先队列，按语义键去重。现在的 2 个后台 + 1 个交互共 3 路合成跑在 2 个推理线程上，可能存在 CPU 过度订阅，建议比较并发 1/2/3 的实际吞吐，再决定是否降低。可考虑在用户评分/播放时暂缓后台合成        |
| audio_ready 风暴 | 批量生成时可能每秒触发数个事件，队列服务应对其做 100～250 ms 的防抖，并只在"预读缓冲未满或新卡位置靠前"时增量加入                                                    |
| 前端预取           | 当前卡播放时，后台读取、校验并解码下一张听音卡的字节，评分后直接切换                                                                                 |
| TOCTOU         | 播放阶段要"读一次字节 → 校验 → 用同一份字节解码"，保证被校验的和被播放的是同一份数据                                                                     |
